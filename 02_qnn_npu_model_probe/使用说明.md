# QNN HTP 模型探针

## 使用说明

### 准备

Windows 命令行能执行 `python --version` 和 `adb devices`，Python 需为 3.10 或更新版本。编译模型还需安装 QAIRT SDK 和 Android NDK。

### 1. 生成模型和模型输入资源

双击 `build_model_assets.bat`，依次输入：

1. SDK 路径，默认 `E:\QualComm\AIStack\QAIRT\2.46.0.260424`。
2. NDK 路径，默认 `D:\Sdk\ndk\27.2.12479018`。
3. 输出目录，默认本目录下的 `model_assets_版本`；已存在时自动添加时间戳。

每项直接按回车使用默认值。成功后得到 `model/libconv_relu_quantized.so`、两组 `.raw` 和 `inputs/input_list.txt`。

**注意**：当前模型库并未针对soc芯片编译成的bin文件，而是模型库。目标设备是ARM64 CPU。 所以兼容不同soc架构的设备

| 对比       | 当前生成的模型库 `.so`                        | 序列化模型 `serial.bin`（QNN context） |
| ---------- | --------------------------------------------- | -------------------------------------- |
| 保存的内容 | 构建模型图的代码、权重、量化参数              | 已针对目标 HTP 准备好的执行数据        |
| 编译目标   | Android **ARM64 CPU**                         | 指定 **HTP 架构/SoC**                  |
| 加载模型时 | QNN 在目标设备上构图、优化、准备              | 直接恢复已准备的 context               |
| 可移植性   | 可在满足 SDK、算子等兼容条件的不同 SoC 上使用 | 受目标 HTP、SoC 和运行时兼容性约束     |
| 初始化开销 | 通常更大                                      | 通常更小                               |

### 2. 生成架构检测包

双击 `build_model_probe.bat`，依次输入：

1. SDK 路径：与第 1 步一致。
2. 模型资源目录：第 1 步的输出目录，默认选取对应 SDK 最近生成的资源。
3. 架构：例如 `68`、`73`、`75`，默认 `75`，须与目标设备一致。
4. 输出目录：默认 `Qnn_model_HTP_V架构_时间戳`。
5. 包标签：直接回车即可。

成功后得到完整检测包。手动指定的输出目录必须不存在或为空。请保留 `Qnn_model_HTP_V68`，生成器使用其中的检测脚本作为模板。

### 3. 连接设备并检测

设备开启 USB 调试并授权电脑，进入生成的检测包，双击 `check_npu_model.bat`。

多台设备连接时，在检测包目录打开命令行执行（替换实际序列号）：

```powershell
adb devices
.\check_npu_model.bat -DeviceSerial 设备序列号 -NoPause
```

仅检查电脑上的资源，不连接设备：

```powershell
.\check_npu_model.bat --check-files
```

检测会先删除设备固定目录 `/data/local/tmp/qnn_npu_model_probe`，重建并 push，确认架构后执行 HTP 推理和 CPU 输出对比。不要同时对同一设备运行多个检测。

### 查看结果

- **PASS**：两组输入均完成推理，HTP 与 CPU 输出差异在样例容差内。
- **FAIL**：查看检测包内 `probe_logs/时间戳` 下的日志。
- **文件校验通过**：仅表示文件完整，不代表设备推理通过。

所有脚本使用系统 Python 和 ADB，新包不附带 `tools`。更换 SDK 时，从第 1 步重新生成。

## 功能说明

### 探针验证什么

当前探针使用一个 **8 位量化 Conv2d + ReLU 模型**，在目标设备上分别通过 QNN HTP（NPU）和 QNN CPU 后端执行相同的两组输入，并比较输出结果。

模型输入尺寸为 `[1,299,299,3]`，输出尺寸为 `[1,149,149,32]`。每组输出包含 **710432 个 float32 元素**。

### 检测流程

1. 校验本地资源，检查 ADB 连接及 Android arm64 环境。
2. 检查路径后清理设备固定目录 `/data/local/tmp/qnn_npu_model_probe`，重建并 push；失败立即停止。
3. 查询设备实际 DSP 架构，与检测包不匹配时停止模型推理。
4. 使用 HTP 后端执行两组输入，再使用 CPU 后端执行同一模型和输入，获得对照输出。
5. 下载输出，检查模型名、后端和两次推理完成记录，逐元素比较 HTP 与 CPU 结果。

设备文件保留到下次检测时清理，电脑日志按时间保存在 `probe_logs`。同一设备不要同时运行多个模型探针。

### 正确性判定

每组输出必须尺寸正确、数值有限（无 NaN 或无穷值），且所有元素的 HTP/CPU 绝对误差均不超过：

`2 × 0.0547085 + 0.000001 = 0.109418`

`0.0547085` 是模型输出量化步长。探针采用两个步长加浮点余量作为容差，用于容纳不同后端的量化计算和舍入差异；这是当前样例的测试标准。

**PASS 表示该量化模型在当前设备上推理成功，两组测试输入的 HTP 输出均通过 CPU 对照校验，结果在设定容差内一致。** 这确认了本次两组输入的测试通过，不代表已验证所有可能输入。

推理失败、完成记录不符、输出异常或任一元素超过容差，都会报告 **FAIL**。失败原因需结合日志判断，不能仅凭 FAIL 认定设备不支持 NPU。

### 控制台字段

| 字段 | 含义 |
| --- | --- |
| `Sample 0 / 1` | 第 1 / 2 组测试输入，每组分别在 CPU 和 HTP 上执行 |
| `max error` | 该组所有输出元素中，HTP 与 CPU 的最大绝对差，不是百分比 |
| `tolerance` | 允许的绝对误差上限，当前为 0.109418 |
| `mismatches` | 误差超过容差的元素数；0 表示全部在容差内，不表示逐位相同 |

只有推理、完成记录检查和两组输出比较全部通过，最终才显示 PASS。正常检测退出码 0 表示通过，1 表示失败；`--check-files` 仅检查本地文件，不执行推理。

### 日志与原始输出

日志位于检测包的 `probe_logs/时间戳`：

| 文件或目录 | 内容 |
| --- | --- |
| `device_info.txt` / `core_version.txt` | 设备信息 / DSP 架构查询结果 |
| `deploy.txt` | 设备目录清理及资源推送记录 |
| `htp.txt` / `cpu.txt` | HTP / CPU 推理日志 |
| `output_htp/Result_0、Result_1` | 两组 HTP 原始输出 |
| `output_cpu/Result_0、Result_1` | 两组 CPU 原始输出 |
| `comparison.json` | 每组输出的误差及比较结果 |
| `result.json` / `error.txt` | 最终结果 / 失败原因（失败时记录） |

### 验证范围

本探针验证当前模型在当前设备、系统和 shell 环境下的模型图构建、准备、执行及输出一致性。CPU 输出作为对照，不是独立的业务标准答案。

检测通过不代表其他模型、APK 运行权限、长期稳定性、性能、功耗或业务精度也已通过测试。
